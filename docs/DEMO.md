# CloudSentinel Live Demo Guide

## Goal

Demonstrate continuous, context-aware, application-level Zero Trust enforcement.

The central message:

```text
CloudSentinel does not permanently trust a signed-in user.
It continuously evaluates current context and restricts only the resources that carry the greatest risk.
```

## Demo Script

### Step 1: Login

Log in as `developer01`.

Say:

```text
We are signed in as a legitimate developer. The point is not whether the user logged in once. The system continuously evaluates whether this user should access each application right now.
```

### Step 2: Show Normal State

On the Overview page, point to:

- current risk score
- LOW risk level
- healthy posture tags
- application access matrix
- multi-cloud resources

Say:

```text
The user starts with healthy posture: trusted device, MFA verified, compliant OS, active endpoint protection, normal behavior, and normal location.
```

### Step 3: Show Resource-Specific Access

Point to Application Access.

Explain:

```text
Even in a healthy state, critical resources can require stronger controls. Access is evaluated per application, not as one global user allow/block decision.
```

### Step 4: Start Simulation

Click:

```text
SIMULATE ACCOUNT COMPROMISE
```

Say:

```text
This is a controlled account-compromise simulation. It does not run malware or inspect the host machine. It injects deterministic demo telemetry so the Zero Trust pipeline can re-evaluate the user.
```

### Step 5: Narrate Detection Sequence

As the staged sequence appears, call out:

- analyzing endpoint
- new device detected
- location anomaly detected
- suspicious behavior detected
- data exfiltration detected
- behavioral anomaly confirmed
- risk score recalculated
- policies re-evaluated
- critical resources restricted

Say:

```text
The endpoint posture and behavior changed, so CloudSentinel re-evaluates the current security context.
```

### Step 6: Show Risk Escalation

Point to the risk gauge and risk components.

Say:

```text
The risk engine combines identity, posture, behavior, and context risk. The model contributes behavioral anomaly detection, but it is not the entire Zero Trust decision.
```

### Step 7: Show Posture Tags

Point to the changed tags.

Expected examples:

- NEW_DEVICE
- NEW_LOCATION
- AUTH_ANOMALY
- UNUSUAL_ACTIVITY
- DATA_EXFILTRATION
- THREAT_DETECTED

Say:

```text
These tags are generated by the backend posture engine and persisted. The frontend is only displaying backend state.
```

### Step 8: Show Application Access Changes

Point to Application Access.

Expected compromised behavior:

```text
Email: ALLOW or MFA_REQUIRED
HR Portal: MFA_REQUIRED
Cloud Storage: READ_ONLY or DENY
Analytics Service: READ_ONLY or DENY
Customer Database: DENY
Admin Console: DENY
```

Say:

```text
Notice the user is not simply blocked everywhere. CloudSentinel reduces blast radius by restricting sensitive resources while preserving lower-risk functionality.
```

### Step 9: Open Decision Detail

Click Customer Database or Admin Console.

Point to:

- user risk
- resource sensitivity
- security factors
- policy rule
- final decision
- reason

Say:

```text
The policy engine explains why the decision was made. This is the basis for the "Why was I blocked?" experience.
```

### Step 10: Show Events

Point to Live Security Events or Incidents.

Say:

```text
Every important stage is auditable: anomaly, risk escalation, policy re-evaluation, and access decisions.
```

### Step 11: Show Blast Radius

Point to Threat Contained and Blast Radius.

Say:

```text
The system restricted sensitive resources instead of shutting down the entire user. This is application-level containment.
```

### Step 12: Reset Demo

Click:

```text
RESET DEMO
```

Confirm:

- simulation state returns to NORMAL
- risk returns to LOW
- healthy tags return
- access matrix returns to normal

Say:

```text
The demo is repeatable. Reset restores only the demo user's simulated state, not the entire database.
```

## Prototype Boundaries

Be explicit:

- Cloud resources are simulated.
- Endpoint threat signals are simulated.
- MFA is represented as a policy decision.
- Isolation is represented as a policy decision.
- No malware is run.
- No host machine security state is read.
- No real cloud IAM enforcement is performed.
