# CloudSentinel

CloudSentinel is a demo-grade adaptive Zero Trust control plane for multi-cloud access decisions. It shows the core hackathon story behind the product:

same user + same moment + different resource sensitivity = different access decision

The app is designed so the frontend displays access decisions generated by the backend policy engine, not locally computed authorization outcomes. The backend evaluates identity, device posture, telemetry, behavioral anomaly, and resource sensitivity before returning a decision such as ALLOW, MFA_REQUIRED, READ_ONLY, DENY, or ISOLATE.

## Live deployments

- Backend API: https://cloud-sentinel-1-cdvy.onrender.com
- Frontend app: https://cloud-sentinel-dnxt.vercel.app/

## What the repo contains

This repository is organized into a Python FastAPI backend, a React/Vite dashboard, a small ML/anomaly component, and demo docs/scripts. The project is intentionally deterministic and production-inspired in feel, but its cloud resources and telemetry are simulated for the hackathon prototype.

## Product intent

CloudSentinel models a zero-trust control plane that continuously monitors user context and adapts access permission based on real-time risk. The demo focuses on a single user (`developer01`) whose risk score rises through staged attack simulation patterns, while higher-sensitivity resources become restricted while lower-risk workloads remain accessible.

The core demo invariants in this repo are:

- `developer01` starts healthy with risk near 12.
- Attack simulation raises risk through visible stages: 12 -> 35 -> 58 -> 74 -> 91.
- Low-risk resources remain reachable after compromise, while sensitive resources are restricted.
- Reset restores the baseline without code changes.

## Architecture summary

### Backend

The backend is a FastAPI application that includes:

- FastAPI app bootstrap and CORS setup in `backend/main.py`
- SQLAlchemy models in `backend/models.py`
- configuration and environment handling in `backend/config.py`
- SQLite initialization and database session setup in `backend/database.py`
- seeded demo data in `backend/data/seed.py`
- API modules under `backend/api/`
- security modules under `backend/security/`

The system is intentionally modular:

- `telemetry` ingests behavior and endpoint signals
- `posture` and `tags` evaluate trust state
- `anomaly` applies deterministic behavioral scoring using an Isolation Forest model
- `risk_engine` calculates transparent risk scores and explanations
- `policy_engine` makes the final access decision
- `simulation` drives the demo compromise and reset lifecycle

### Frontend

The frontend is a React + Vite + Tailwind dashboard that consumes API data from the backend. It is not responsible for making the final authorization decision; it renders the decision and supporting context returned by the backend.

Main frontend entry points include:

- `frontend/src/App.jsx`
- `frontend/src/pages/*`
- `frontend/src/components/*`
- `frontend/src/services/api.js`
- `frontend/src/hooks/useSimulation.js`

### ML component

The repo includes a lightweight anomaly model in `ml/train.py` and an exported model artifact in `ml/model.pkl`. The Isolation Forest is treated as a contributing signal to behavioral risk, not the entire trust model.

## Demo flow

1. Log in as `developer01`.
2. Browse the dashboard and verify the baseline risk posture.
3. Trigger the simulation attack flow from the UI.
4. Observe telemetry, posture tags, behavioral anomaly, and rising risk.
5. See resource-specific decisions shift as policy re-evaluates access.
6. Reset the demo to return the environment to a healthy baseline.

## Important implementation notes

- The app is intentionally a demo prototype, not a real cloud enforcement system.
- Cloud resources are simulated metadata, not AWS/Azure/GCP integrations.
- Endpoint telemetry and threat signals are generated from deterministic seeded state.
- Multi-factor enforcement and access decisions are returned by the backend policy engine rather than applied natively by a cloud provider.
- The Isolation Forest model is a supporting signal in behavioral risk scoring, not the entire security model.

## Prototype boundaries

This project is deliberately scoped as a hackathon prototype. It does not perform real malware scanning, host telemetry collection, or cloud IAM enforcement. Instead, it demonstrates the control-plane logic and the policy engine behind adaptive, resource-aware zero-trust authorization.
